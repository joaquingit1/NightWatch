# Nightwatch field lessons — 2026-07-24

This document was written before the operator-workbench integration. It is the
regression contract for every change that follows. It records what failed in
real runs, what improved the robot, and which behaviors must not be lost while
adding exploration, sleep analysis, and manual control.

## Definition of done

The demo is complete only when all of the following are true:

1. A fresh launch selects the intended venue profile, loads its saved map,
   relocalizes when possible, and begins the selected autonomous mode without
   operator setup beyond choosing the mode.
2. Exploration continuously seeks useful unknown space, respects focus and
   keep-out zones, remembers visited rooms across restarts, and does not retry a
   failed glass/obstacle approach indefinitely.
3. Sleep-analysis mode patrols autonomously, periodically performs a deliberate
   camera-up scan, detects a stable fatigue candidate quickly, approaches once,
   starts the QR/NFC intake, and either resumes patrol or escorts the visitor to
   the best reachable sleeping area.
4. The scan is an explicit, time-bounded exception to the normal liveness rule.
   No unexplained stationary period lasts more than 10 seconds.
5. Manual takeover is immediate and authoritative. Autonomous navigation,
   interaction policy, and fatigue events cannot refuse it or take control back.
   Releasing a key, losing browser focus, losing the command stream, or leaving
   manual mode sends zero velocity.
6. Switching among Autonomous Exploration, Sleep Analysis, and Manual Override
   is seamless, observable, and leaves exactly one movement owner.
7. Existing mapping, A* navigation, dynamic-obstacle, glass/failure-zone,
   relocalization, venue, focus-area, keep-out, fast fatigue, video, TTS, and
   semantic-area behavior remains intact unless a focused test proves a change
   is required.

## What went wrong in field runs

### Long stationary periods had several distinct causes

- Startup correctly used `SENSORS_NOT_READY`, but the operator could not tell
  whether this was a bounded startup gate or a dead system.
- Navigation sometimes reported that movement was expected while odometry moved
  only 0–0.01 m over the eight-second liveness window.
- Repeated failures near the same coordinates caused cancel/replan/escape
  cycles. After three escapes in five minutes, the old supervisor entered
  `STUCK_HELP` and intentionally waited for human help. That is incompatible
  with an unattended booth run.
- Social actions and fatigue analysis acquired movement ownership even when the
  action did not require the robot to remain still. Repeated `Hello` actions
  could therefore look like random waving and suppress navigation.
- Earlier sleep-analysis logic waited for a person or asked people to look at
  the dog. People simply walked away while the robot remained stationary.
- Some server/bridge loops did duplicate work, increasing latency and making
  robot state appear stale.

Lesson: every zero-velocity interval needs a named owner, reason, deadline, and
next transition. A timeout must resume or recover; it must never silently become
an indefinite hold.

### Glass and difficult obstacles were memory failures as well as perception failures

- LiDAR can under-report glass, so a planner may repeatedly consider a point
  traversable even after the body cannot make progress.
- Merely replanning to the same frontier repeats the same failure.
- The useful behavior was: detect lack of progress, cancel the current goal,
  reverse/turn to create clearance, add a temporary local failure penalty, and
  choose a meaningfully different frontier.
- A failure penalty must survive long enough to prevent immediate retry, but it
  must not permanently convert a person or other moving obstacle into a wall.

Lesson: use both proactive costmap avoidance and reactive experience. Classify
short-lived obstruction evidence as dynamic; promote repeated spatial failures
to a longer-lived glass/blocked-region penalty. Do not disable A* or bypass the
current local safety layer.

### Dynamic obstacles should not erase the route unnecessarily

- The current A* route is valuable global intent.
- A person crossing the path should cause a bounded local wait/dodge and then a
  continuation/replan to the same goal.
- Repeated cancellation and selection of a brand-new exploration goal produces
  circles and revisits.

Lesson: retain the global goal for transient obstacles. Replan the path to the
same goal after a bounded obstruction interval; abandon the goal only after
evidence that the region itself is persistently blocked.

### Map persistence is a coordinate-frame and startup contract

- Saving a map file is insufficient if the next run does not select it, if
  relocalization never accepts the live cloud, or if semantic areas and zones
  are stored only in the previous run's local frame.
- Logs repeatedly showed the premap path being supplied while relocalization
  skipped clouds below `MIN_LOCAL_POINTS=50000`.
- Legacy semantic areas without persistent map coordinates were deliberately
  excluded from cross-session lookup; that prevents stale coordinates from
  becoming unsafe destinations, but also explains missing old annotations.
- A focus area appeared shifted/disappeared when its coordinates were not
  transformed consistently with the displayed/relocalized map.
- A new venue must never overwrite another venue's map, zones, or semantic
  areas.

Lesson: venue selection owns one versioned bundle: point cloud, occupancy data,
relocalization metadata, semantic areas, focus/keep-out zones, and display
transform. The UI must show whether the bundle was loaded and whether the robot
is localized; it must not imply that an old map is active when only a file path
was found.

### Fatigue detection was too slow and too passive

- The older model defaults required roughly five seconds of assessment, eight
  seconds of initial observation, and twenty calibration frames. Many visitors
  had already left.
- The current faster analyzer uses a short assessment window, a two-second
  initial observation, six calibration frames, and absolute head/gaze evidence
  before personal calibration completes.
- The camera is low while walking. Passive patrol frames often do not contain a
  usable face.
- Stopping indefinitely or verbally asking for attention is worse than a short,
  purposeful scan.

Lesson: in Sleep Analysis mode only, periodically pause at a safe navigation
boundary, lower the rear to pitch the camera upward, scan for a strictly bounded
window, then restore the normal stance and resume the same mission. Detection
should run continuously, but a scan is the high-quality capture opportunity.
Only a stable tracked fatigue candidate may trigger approach/interaction.

### Waving was not a reliable wave detector

- A static raised-arm pose was treated as a hand wave.
- `Hello` could also be scheduled randomly or triggered by prolonged gaze, so
  images and logs did not prove that a person's wave caused the response.
- Waiting for navigation to become idle made responses arrive after the desired
  2.5-second window.

Lesson: keep separate causes for human-wave, sustained mutual gaze, and ambient
personality actions. Human-wave detection needs temporal wrist motion,
shoulder-normalized amplitude, track continuity, cooldown, and saved trigger
evidence. Acknowledge quickly with nonblocking audio; schedule a physical paw
wave only at a safe movement boundary unless hardware testing proves it can be
performed while walking.

### Video/server latency harms the whole pipeline

- Unbounded frame queues, repeated encoding, per-client inference, and overly
  frequent UI updates create stale video and starve perception/control.
- A visually smooth but seconds-old stream is not useful for face interaction.
- Map rendering was acceptable; repeated map-polish work did not improve the
  critical robot loop.

Lesson: capture once, keep only the newest frame, analyze at a controlled rate,
cache annotations, and fan out the latest encoded frame. Robot command and
navigation loops must have priority over browser streaming. Report frame age,
not just nominal FPS.

### The public QR/NFC path was incomplete

- The public form could load, but its schema returned no active
  `interaction_id`.
- Mirroring only a submission to the local server cannot bind that submission
  to the visitor currently standing in front of the robot.
- Browser Web NFC support is too limited to be the primary demo path.

Lesson: program the NFC tag as an ordinary HTTP(S) URL NDEF record, the same
destination as the QR code. The public form must obtain a signed, expiring
interaction token generated by the local active session. Submissions need
idempotency and a small outbox/retry path so temporary tunnel loss does not lose
the answer.

## What made the robot work better

- Keep the current A* planner and local safety layer.
- Preserve the active goal across transient moving obstacles.
- Penalize repeated failure locations and select spatially distinct frontiers.
- Use map-aware revisit scoring rather than treating every restart as a blank
  floor.
- Persist data by venue and expose venue/map/localization status in the UI.
- Keep focus and keep-out zones as first-class map-frame data.
- Use the current fast fatigue analyzer and a newest-frame-only pipeline.
- Treat multiple sleeping areas as semantic destinations and choose the nearest
  reachable one by navigation cost, not Euclidean distance alone.
- Keep social reactions subordinate to navigation ownership.
- Make startup and every intentional hold observable.

## Control ownership contract

Exactly one movement owner may publish effective velocity:

1. `safety` can always force zero velocity.
2. `manual` has priority over every non-safety owner and remains latched until
   the operator explicitly returns to an autonomous mode.
3. `escort` owns autonomous motion only during an accepted escort.
4. `interaction` may request a bounded stop/stance but cannot override manual.
5. `sleep_scan` may request a bounded stop and camera-up stance only in Sleep
   Analysis mode.
6. `exploration` or `patrol` owns ordinary autonomous motion.
7. Social actions never acquire route ownership.

All commands carry a monotonic sequence number and timestamp. Manual velocity is
sent at a fixed cadence and expires to zero after 500 ms without a fresh
command. A mode transition first stops the old owner, confirms the new state,
and only then enables the new owner.

## Mode contract

### Autonomous Exploration

- Mapping and frontier exploration only.
- Fatigue analysis and social interaction disabled.
- Map, focus/keep-out, liveness, and safety remain enabled.

### Sleep Analysis

- Autonomous patrol/exploration continues.
- Fatigue analysis runs continuously.
- A bounded camera-up scan is allowed on cadence.
- Stable fatigue detection can transition through approach, greeting, intake,
  escort decision, escort, farewell, and patrol resume.
- Fatigue events are gated during active interaction and escort so another
  person cannot steal the session.

### Manual Override

- Direct operator velocity and posture/action commands.
- Autonomous publishers are muted and cannot auto-take over.
- The map, video, telemetry, and optional passive fatigue visualization may
  continue, but they cannot issue movement.

## Sleep-scan safety contract

- Enter only from Sleep Analysis mode and only after the navigation controller
  acknowledges a safe stop.
- Cancel/pause the current route without discarding its goal.
- Use the verified Go2 posture/action primitive that lowers the rear and raises
  the camera view; do not invent motor-level joint commands.
- Maximum scan duration and maximum stance duration are hard deadlines.
- A candidate must have stable tracking and enough quality/confidence before
  approach.
- On no candidate, timeout, mode change, manual takeover, disconnect, or error:
  restore normal stance, release scan ownership, and resume/replan the retained
  route.
- Manual takeover must preempt the scan immediately.

## Change discipline

- Use the current working tree as the navigation/mapping/perception base.
- Selectively port the other developer's workbench, form, and interaction-state
  concepts. Never merge the older robot stack wholesale.
- Keep patches narrow and tests adjacent to each behavior.
- Do not weaken or delete a regression test to make a port pass.
- Do not command live motion merely to test an uncertain API. Verify against
  DimOS and the Unitree driver first; use a fake transport for automated tests.
- Before a live run, show the active venue, map path, localization state, mode,
  movement owner, current hold deadline, command age, and emergency-stop state.

## Required validation

1. Unit tests for transition legality, priority, timeout, stale-command stop,
   scan cleanup, route retention, fatigue gating, and intake idempotency.
2. Server contract tests for every operator command and status field.
3. Browser tests for keyboard down/up, blur, visibility loss, mode switch,
   disconnected state, map/zone persistence, and active interaction display.
4. Offline end-to-end simulation covering:
   exploration → sleep mode → scan timeout → patrol resume;
   scan → fatigue candidate → intake timeout → patrol resume;
   scan → accepted help → best sleeping area → farewell → patrol resume;
   and manual takeover from every state.
5. A supervised live test in a focus area only after all offline tests pass.
